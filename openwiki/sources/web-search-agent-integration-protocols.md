## Durable facts adopted (condensed)

- The **2026-07-28 MCP specification** is the current revision: stateless core (no handshake/sessions; `initialize`/`initialized` and `Mcp-Session-Id` retired per SEP-2575/SEP-2567, optional `server/discover` RPC), MRTR (SEP-2322), header-based routing (SEP-2243), cacheable list results (SEP-2549), authorization hardening, formal extensions framework, Tasks as an extension (SEP-2663), deprecations, and a formal deprecation policy; RC was 2026-05-21.
- **MCP authorization** is OAuth 2.1-based; **CIMD (Client ID Metadata Documents — an HTTPS metadata URL used as the client ID) replaces DCR for new implementations**, with DCR now **formally deprecated** (kept for backward compatibility, removed in a future version); RFC 9207 `iss` validation is required of clients, `application_type` set during DCR, and client credentials are issuer-bound (SEP-2468/837/2352). Software statements are optional for `localhost`-impersonation trust, with SSRF protections for authorization servers making outbound requests.
- **2026-07-28 deprecations:** Roots, Sampling, and Logging (SEP-2577) plus the legacy HTTP+SSE transport — they keep working for at least **twelve months**; new implementations shouldn't adopt them.
- **MCP Registry** launched in preview (2025-09-08) as an open catalog/API for public MCP servers; by the 2025-11-25 anniversary it held ~2,000 entries (407% growth from September), and the 2025-11-25 release added an enterprise self-managed registry vision.
- **2026 roadmap**: releases → Working Groups; priority areas transport evolution/scalability, agent communication (Tasks lifecycle gaps), governance maturation (contributor ladder, delegation), enterprise readiness.
- **Tier 1 SDK posture:** TypeScript, Python, Go, and C# all speak 2026-07-28 on release day (migration notes included); Rust SDK in beta. The **TypeScript SDK shipped a v2.0.0 monorepo split** (core/client/server/node/hono/fastify/express/server-legacy/codemod at 2.0.0, following 1.30.0); Go `v1.7.0-pre.1` and C# `2.0.0-preview.1` were the observed beta packages; Swift through 0.12.1 with 0.11.0 covering 2025-11-25 conformance + SEP-973/1034/1036/1330 but not Tasks/sampling-with-tools/auth.
- **2025-11-25 revision (prior stable) detail added:** experimental core Tasks with states `working`/`input_required`/`completed`/`failed`/`cancelled`; CIMD URL-based client registration (SEP-991); the extensions concept (optional, additive, composable, independently versioned); security features (SEP-1024, SEP-835).
- **MCP Apps extension detail re-confirmed/extended:** 4-phase UI lifecycle (discovery, initialization, data delivery, interactive), `content` vs `structuredContent` separation, Python SDK (`mcp`) alongside TS (`@modelcontextprotocol/ext-apps`), Java SDK support **missing** as of v0.17.2 (issue #780); SEP-1865 (csharp-sdk #1431) frames it as the first official extension co-developed by Anthropic and OpenAI.
- **New companion repo surfaced:** `modelcontextprotocol/mcpb` releases (v2.1.2 latest observed; v2.1.0 adds experimental UV runtime support in manifest v0.4 and removes `_meta` from manifest v0.1) — a packaging/registry companion, tracked on the releases reference.

## Durable facts adopted (2026-08-22 re-pull, condensed)

- **MCP lifecycle policy** — the feature lifecycle is now *Active → Deprecated → Removed* with **at least twelve months** between deprecation and earliest possible removal (SEP-2596); Standards Track SEPs can no longer reach Final status until a matching scenario lands in the **conformance suite** (SEP-2484), the same suite the **SDK tier system** (PR 1777) scores official SDKs against. Foundational-change rationale: "with deprecation windows and extensions as the standard tools going forward, implementers targeting `2026-07-28` will be able to adopt future revisions without rewriting their transport or lifecycle code."
- **Full JSON Schema 2020-12 for tools (SEP-2106)** — tool `inputSchema`/`outputSchema` lifted to full JSON Schema 2020-12: input schemas keep the `type: "object"` root but allow composition (`oneOf`/`anyOf`/`allOf`), conditionals, and references (`$ref`/`$defs`); output schemas are unrestricted; `structuredContent` can be any JSON value, not only an object. Implementations must not auto-dereference external `$ref` URIs and should bound schema depth and validation time.
- **Error-code change (SEP-2164)** — the missing-resource error changes from MCP-custom `-32002` to JSON-RPC standard `-32602` Invalid Params; clients matching on `-32002` must update.
- **RC timeline/validation** — RC locked 2026-05-21; final spec 2026-07-28; ten-week window for SDK/client validation; full RC in the draft specification (`/specification/draft`), changelog against `2025-11-25`.
- **Java SDK v2.0.0 GA** — first major since 1.x (milestones M1–M3 + RC1); tracks **2025-11-25** spec; breaking changes (`JsonSchema`/`Map`/`inputSchema`), new `meta`, transport customization hooks + `McpHttpClientAuthorizationErrorHandler`, logging updates, `McpStatelessSyncServer#closeGracefully`, `Resource`/`ResourceTemplate` fixes; migration guide (MIGRATION-2.0.md); v0.18.3 patched GHSA-hv2w-8mjj-jw22. **MCP Apps support still absent** — the Java SDK Apps gap persists past v2.0.0.
- **MCP Registry open-source depth** — the official registry service at <https://registry.modelcontextprotocol.io> is implemented by the open-source `modelcontextprotocol/registry` Go repository (permissive license, ~7.2k★/947 forks, 686 commits, registry working group maintainers) with a parent OpenAPI spec enabling compatible sub-registries — public opinionated marketplaces per client and private enterprise registries sharing API schemas; community-driven moderation (spam/malicious/impersonating denylisting).
- **MCP Apps interface surface deepened** — UI resources are declared up-front during tool registration via `ui://` URIs in `_meta.ui.resourceUri`; Views communicate with the Host via **JSON-RPC over `postMessage`**; tools are optionally `visibility: ["app"]`-only so UI interactions (refresh, pagination, form submit) don't bloat the model's context; Hosts provide context (theme, locale/timezone, display mode, container dimensions, platform) plus CSS custom-property theming; displays support inline/fullscreen/pip with host final say; the lifecycle adds a **5th Teardown phase** (`ui/resource-teardown`); progressive enhancement: hosts advertise UI support, servers gate UI-enabled tools — "UI is a progressive enhancement, not a requirement."
